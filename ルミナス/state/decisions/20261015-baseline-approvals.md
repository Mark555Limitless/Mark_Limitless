# ADR 2026-10-15: 素体の名簿 v0・保護設定・最終提案 §11・現行手順の記録の承認

- 背景: 素体の開発を開始（Mark の方針「最初は小さく、柔軟性と今後の発展性に重点」）。名簿 v0 と P4 ゲートができ、Mark の判断が要る 4 点を示した
- Mark の決定（原文）: 「1から4まで全て承認。」
- 決定の内容:
  1. **名簿 v0（`config/roster.json`、7 行）を承認**。承認の対象の組は各行の（提供元・モデル・版の種類・役割・最大の送信区分・上限）。承認者 Mark、日付 2026-10-15、確認期限は各行の `review_by`（2026-11-15）。Luna の行は「保留」のまま（下の 3-1）
  2. **名簿を確認つきのファイルにする**: `.claude/settings.json` の `permissions.ask` に `Edit(/config/roster.json)` を追加（Bash での書き換えは guard-protected の対象外なので、名簿の変更は Edit で行う運用とする）
  3. **最終提案 `docs/proposals/20261015-prototype-baseline.md` §11 を既定値で承認**:
     - 3-1 予算: 追加の API 支出は上限が決まるまで 0 円。Codex 共有枠のルミナスへの割り当ては暫定で月の 10%・週はその 1/4。**Luna は契約上の上限を確認するまで使わない**（名簿で保留）
     - 3-2 時間: Mark の作業は週 3 時間まで（記録は 1 日 10 分）、月次の監査は 30 分
     - 3-3 最初の用途は週次の AI 調査（検証デスク）。監視リスト（約 15〜20）は P2 で提案し、Mark が承認する。対外発信には使わない
     - 3-4 照合と採点: 月次のレビュー役（調査役と別）と Mark の確認。独立した採点者がいなければ性能の主張はしない
     - 3-5 P3（調査役の定義＝保護ファイル）と P4（`tools/`・`orch/`）の実装は、指示書→Codex→試験→Opus の審査の流れで進めてよい
     - 3-6 見落とし台帳の独立ソース: (c) 公式の更新履歴を主軸、(a) Mark の気づきを補助、(b) 公開ニュース発信は手がかり
     - 3-7 Codex スレッドの CLI 再開は行わない（見送り）
     - 素体の完成条件 6 つ（最終提案 §6）
  4. **現行手順の記録（P0）を開始**。記録の置き場は `state/p0/`（1 回の週次調査につき 1 枚。様式は `docs/baseline/weekly-report-template.md`）。サイクル 0（2026-10-14）の記録は司令塔が起こす
- 影響: 名簿の変更は以後、確認のダイアログが出る。ゲートの上限は名簿の値で効く。週次の調査の上限は初月の仮置き（15 万トークンまたは 30 分）

## 追記 2026-10-15: P0 の記録は司令塔が行う
- Mark の指示（原文）: 「下記はキミが実行してください 'Mark へのお願い: 次の週次 AI 調査のときから、作業時間（分）と気づいたことを、state/p0/ に記録してください（1 日 10 分まで）。'」
- 決定: P0 の記録は司令塔が週次の AI 調査のたびに書く（ROUTINE §4 に追加）。Mark の作業時間は、会話から分かる範囲（指示・承認の回数と承認待ちの時間）を司令塔が記録し、Mark に記入を求めない。§11 の「Mark の作業は週 3 時間まで」は上限として残す
- 影響: Mark の手作業の負担が減る代わりに、会話の外での Mark の作業時間は測れない。これを P0 の記録の限界として毎回明記する
