## 0. 結論

1. **Jev は「判断の部品」で、文章を書く AI ではない。** 文書（state）と型のある問い（Choice・Score・Noul）を渡すと、約 0.1 秒で確率つきの答えを返す。生成・要約・計算・日付の比較はできない。
2. **はっきりした強みは速さ。費用の差は比べる相手で大きく変わる。** 速さは第三者評価機関 Vals AI でも確認された（1 問でも GPT-6 Astra の 47 分の 1 の時間）。費用は、最前線の高価なモデルと比べると 138〜498 分の 1 だが、同じ正解率の最も安い LLM（GPT-6 Luna）と比べると約 3〜4 分の 1 にとどまり、バッチ割引の価格では差がなくなるという論文もある（§6.1 の表）。
3. **精度は課題で分かれる。** 易しい分類と主張の検証では最前線の LLM と同等。法律の推論（LegalBench）では 12 システム中最下位、医療の診断でも大差で負けた。最前線の LLM に勝つことは示されていない（中くらいのオープンなモデル Qwen3.8-27B には多くの課題で勝つ）。
4. **確率の当たり方（校正）は課題ごとに違う。** ある課題では 12 システム中最良、別の課題では最悪だった（Vals AI）。問いごとに自前のラベルで閾値を決めるという今の評価設計が、第三者の結果でも裏付けられた。
5. **日本語は未知数。** 公式は「英語が主。CJK も扱えるが同じ精度ではない」。第三者の論文では多言語の読解で英語 97.2%、122 言語で全体 86.7%・中央値 91.1%、中国語の試験で 83.9%。日本語だけの数値は論文の本文には無い（論文は全応答を公開しているので、取り出せる見込みはある）。問いは英語で書き、日本語の文書は別に測ってから使う。
6. **価値が出る使い方は「大量の安い一次ふるい」と「確信度で人や上位モデルへ回す仕組み」。** 通す判断・安全の境界には使わない（公式も「セキュリティ境界ではない」と書いている）。
7. **ルミナスでの第一候補は 3 つ**: ①出典の種類（一次情報・自己申告・噂）を見分ける止める信号、②引用が主張を裏付けない・矛盾するものを見つける検査、③どのモデルから始めるかの助言（Mark の指示 [1]・CHARTER I-8）。どれも、第三者の文章を送ってよいかの Mark の判断（§8）と、影での測定の後。
8. **実装の不具合を 1 件見つけて直した**（§10）。Jev の Score の答えを、本番ではほぼ毎回「形式不正」として捨てていた。

## 1. Jev とは何か（①）

- TypeSafe の主力モデルで、最初の「System One」モデル。名前はカーネマンの「速い思考（システム1）」から
- LLM と同じく自然言語を理解するが、**文章を生成しない**。答えは型のある値と確率だけ
- 学習法は RLCD（校正された判断のための強化学習）。人の好み（RLHF）でも検証できる報酬（RLVR）でもなく、「確率が当たる割合と一致する」ことを目標にする。詳細は非公開
- 1 回の呼び出しで、1 つの state に多数の問いを並列・独立に当てる。問いを増やしても応答時間はほとんど伸びず、問い同士が影響しない
- 全利用者が同じ重みを使う。顧客データでの追加学習はない。自分の知識は state に、規則は問いの `instructions`・`criteria` に入れる
- Claude Code や Codex の中身として差し替えるものではない（公式「Jev with coding agents」）。エージェントが書くコードの中で、判断の部品として呼ぶ

### 3 つの問いの型

| 型 | 聞くこと | 返るもの | 上限 |
|---|---|---|---|
| Choice | 選択肢から 1 つ選ぶ | `choice`・各選択肢の `probabilities`・`confidence` | 選択肢 255 個（事例集の 1 本は「約 240 まで確実」） |
| Score | 段階の尺度で採点 | `score`（段階番号×確率の和。例 1.43）・`legend`・`probabilities`・`confidence` | 段階 2〜10（11 はサーバーエラー） |
| Noul | 文が真かどうか | `noul`（0〜1） | 確信度は返らない。公式の換算は \|2p−1\| |

## 3. 確信度の仕組み（①）

- Choice: (p_max − 1/n) ÷ (1 − 1/n)。均等なら 0、1 つに集中なら 1。上位 1 つしか見ないので (0.6, 0.3, 0.1) も (0.6, 0.2, 0.2) も 0.4
- Score: 最も確からしい段階からの「確率で重み付けした距離」を、均等な場合の距離で割って 1 から引く。隣の段階に割れるより、両端に割れるほうが低くなる
- Noul: 確信度はなく、0.5 に近いほど不確か。換算するなら \|2p−1\|
- 確信度は確率分布から式で計算した値で、別の情報が足されているわけではない（Vals AI も同じ指摘）。公式は、上位の確率そのものと「1 位 ÷ 2 位」の比も実用的だとしている
- 公式の使い方の基本は 3 段: 高い → 自動で進む／中 → 確認か上位へ／低い → 動かない（人・別の仕組みへ）。閾値は操作の重さで変える。**ルミナスでは「高い → 自動で進む」を「次の検査へ進む（GO ではない）」と読み替える**（`docs/eval-design.md` §4）
- 校正は「多数の予測の集まり」での性質で、個々の答えの正しさは保証しない（公式の注意）
- **公式の資料には**校正の測定値（信頼度図・ECE）が見当たらない。第三者の測定は §6 にある

## 4. 既知の弱点（公式「Jev 1.13 jaggedness」、2026-10-02 版①）

| # | 弱点 | 公式の対策 | ルミナスでの注意 |
|---|---|---|---|
| 1 | 字義どおりに読む（否定・範囲の言葉を額面どおり） | 条件と境界の例を criteria に書く | 問いは短く直接に |
| 2 | 計算・数えること・数値の近さ。Score の期待値から数値を補間で復元することも不可 | コードで計算する。Score の期待値は閾値との比較だけに使う | **ベンチマークの数値の比較はコードで**行い、Jev に聞かない |
| 3 | 日付の前後・間隔 | 年月日を Choice で取り出し、比較はコード | 発表日・論文の版の新旧はコードで |
| 4 | 二重否定・何段もの参照 | 参照を減らし、state の該当箇所を名指し | |
| 5 | 無関係な内容が多い大きな state | 先に絞って必要な部分だけ送る | 記事全文ではなく該当段落を送る |
| 6 | **敵対的な内容**（埋め込まれた指示・誤誘導・自分の分類を主張する文） | criteria を明確にし、配備前に試す | **注入された文で答えが動く。** 止める信号には使えても、通す判断の根拠にしない |
| 7 | instructions と criteria の矛盾 | 両者をそろえる | 「真＝いいえ」のような逆の Noul を作らない |
| 8 | **Choice の選択肢の順番**（先頭に寄ることがある） | 並べ替えて答えが変わらないか確かめる | 第三者の論文では、試験問題（MMLU）で選択肢を回しても正解率は変わらなかった。課題によるので、評価で並べ替え試験をする（§9） |
| 9 | 文章の生成 | 生成モデルを使う | 抽出は「候補を正規表現か LLM で出し、Jev が選ぶ」 |

> 事例集の多くは一つ前の版 `jev-1.12` で測られている（自己一貫性の 2 本だけ `jev-1.13.0`）。全事例が英語のデータ。

|---|---|---|---|
| 自己一貫性（Choice 8 問 × 15 回） | 境界的な投稿の審査 | 同じラベルを返す割合 90.8%（LLM 87.5〜100%）。8 問中 2 問でラベルが割れた | Haiku t=0 の方が安定（100%）。精度は測っていない |
| 自己一貫性（Noul 14 問 × 15 回） | 保険請求の振り分け | 確率の標準偏差 0.0102。0.5 をまたいで揺れた問いが 1 つ | LLM 側の数値は本文に無い |
| 問いをまとめる | 5 万 4 千字の文書に 13 問 | 1 回 $0.000497・0.27 秒、13 回に分けると 12.2 倍高く 10.0 倍遅い | 分けた側は逐次実行の合計 |
| 再ランク | 判例検索（BM25 の上位 30 件） | 1 位が正解 5%→18%、上位 10 件に正解 38%→62%。1,200 回で $0.0645 | 比較は BM25 だけ。40 問 |

| 引用の検査 | LLM の引用が裏付けか・矛盾か・無関係か | 仕込んだ誤り 4 件をすべて検出（2 件は人への回付で） | 8 件の自作 |

| 特徴量の発見 | ワイン評の点数予測（2,000 件） | 予測の誤差（RMSE）: 平均で当てる 3.09・単語の数え上げ 2.47・Jev に点数を直接聞く 2.15・Jev の 38 問を CatBoost に入れる 1.77 | 1 データセット |

### 6.2 第三者評価機関（②）
**Vals AI「An Independent Evaluation of TypeSafe's Jev」（2026-10-06）〔確認済: 本文〕** — 12 システムを 2 課題で比較
- SEC の年次報告書の抜粋で主張を検証する 400 件（Vals の自作）: 全システムが 0.953〜0.995。Jev は 0.975 で最前線の LLM と同等
- LegalBench の 12 小課題（事前登録。12 課題 × 33 問の小さな抜粋で、公開データなので LLM が学習時に見ている恐れがあると Vals 自身が注記）: **Jev は 12 システム中最下位**（クラスの偏りを補正した正解率 0.730。Haiku 4.5 の 0.732 とほぼ同じ。首位は GPT-5.6 Terra の 0.932）
- 校正（ECE）: 主張の検証では 0.011（12 中最良）、LegalBench では 0.108（12 中最悪）。**ある課題での校正は別の課題に移らない**（悪化の一部は「正解率が下がると誤差が増える」機械的なものとも書いている）
- 誤り 1% の予算で閾値を固定すると、95% を自動化できたが、別に取っておいた 265 件での実際の誤りは 1.6%（約 4 件。予算超過。12 中 6 システムが超過）
- 資金提供の開示は本文に見当たらない

### 6.6 第三者の評価から言えること
1. **速さは本物。** 測り方で倍率は 2〜200 倍と割れるが、方向は一致
2. **費用は比べる相手と価格の形で逆転しうる。** 最前線の LLM よりは桁違いに安いが、同じ正解率の安い LLM との差は数倍で、バッチ割引なら差が無いこともある
3. **精度は「易しい分類なら最前線の LLM と同等、難しい判断では負ける」。** 型のある出力そのものが精度を上げるわけではない
4. **校正は課題ごとに違う。** 問いごとに自前のラベルで閾値を決める必要がある（今の評価設計どおり）
5. **注入への強さは条件次第。** 3 択の作り直しでは攻撃の成功はまれだったが、既定の閾値では注入を取りこぼし、高い確信で誤る攻撃も報告されている。止める側の信号としては使えるが、境界にはしない
6. **「該当なし」を選ぶのが苦手。** 算術で 7%・医療で 10.5%。「不明」の選択肢を入れても、閾値を調整しないと効かない

## 7. 得意・不得意のまとめ

**向く仕事**
1. 決まった観点での一括判定（1 文書に十数問）
2. 確率で「次の検査へ・人へ・止める」に振り分ける仕事（トリアージ・ガードレール・引用の検査）
3. 閉じた選択肢から選ぶ仕事（分類・振り分け・候補からの抽出・階層分類）
4. 高いモデルの前の安いふるい（怪しいものだけ上位へ）
5. 意味の判定を数値の特徴量にして、普通の機械学習に渡す仕事（ただし、出力で自前の分類器を学習させるのは MCA 2.3(b) の射程を Mark が確認するまで行わない）

**向かない仕事**
1. 文章の生成・要約・翻訳
2. 計算・数の比較・日付の比較・数えること
3. 候補を前もって用意できない抽出、255 を超える選択肢、「該当なし」が多い問い
4. 安全の境界、正しさの保証（注入で動く・閾値の近くで答えが割れる）
5. 何段もの推論が要る判断（System 2 の仕事は Claude へ）
6. 日本語が中心の判断（自前で測るまで）

## 8. ルミナスと AI NEWS Select での使い道（優先順）

**前提**
- Jev は助言で、**止める側の信号から使う**（`docs/eval-design.md`）。通す判断・取り消せない操作の承認には使わない（CLAUDE.md 不変条件 1）
- 送るのは「公開可」の内容だけ（`docs/support-ai.md` §7・`VIRTUAL_MARK.md` §6）。**使い道 1・2・4 は、第三者の記事・論文・Web ページの本文を Jev に送る新しい外部送信にあたる。** 「公開されている Web の本文を公開可に準ずるものとして送ってよいか」を Mark に一度確認する。承認までは、このリポジトリの公開済みの文書など公開可のものだけで試し、第三者の本文は送らない。承認後も、人名を落とし、該当段落だけを送る（弱点 5）
- 問いの中の `{…}` は Choice の選択肢を表す

| 順 | 使い道 | 問いの形（例） | 価値 | 注意 |
|---|---|---|---|---|
| 1 | **出典の種類の判定**（CHARTER I-6 の信頼度ピラミッドと利益相反） | Choice「この数値を測ったのは誰か」{開発元の自己申告・第三者評価機関・査読論文・不明}。Choice「この記事の主張の出どころ」{公式発表・査読/会議・一次情報を引いた報道・匿名情報源や噂・不明} | 自己申告のベンチマークや噂の段階の記事を、安く全件ふるえる。止める側の信号にちょうどよい | ドメインで決まる部分（公式ドメイン・査読誌・通信社）はコードの表で先に決める。Jev は URL を開けず、本文の主張だけで判定する。「公式発表によれば」と書くだけで寄る（罠問題で測る）。「該当なし」を選ぶのが苦手な傾向（算術 7%・医療 10.5%）なので、「不明」の選択肢を入れたうえで閾値を自前で決める |
| 2 | **引用・要約の裏付けの検査** | Choice「この段落はこの主張を」{裏付ける・矛盾する・何も言っていない}。数値はコードで正規表現で取り出して突き合わせる | CHARTER I-6 の「論文の要旨・数値・結論を直接確認し報道の要約と照合」を手伝う。「裏付けない・矛盾する」とされたものを止めて Claude に回す | **Jev が「裏付ける」とした分も、数値・結論の照合は Claude が行う**（通す判断に使わない）。通った分の 10% は Mark が監査（`docs/eval-design.md` §5）。公式の事例は 8 件だけ。言い換えた引用は文字列照合で落ちるので、あいまい照合が要る |
| 3 | **どのモデルから始めるかの助言**（Mark の指示 [1]・CHARTER I-8） | 作業の説明を state に、Noul を数問（「複数ファイルにまたがる変更か」「Web の一次情報の確認が要るか」「判断に迷う論点があるか」）。段階はコードで合成 | 約 0.1 秒・ほぼ無料で、毎回の作業に「どのモデルから始めるか」の根拠を付けられる。`docs/support-ai.md` §9 の実験 A（実際に足りたモデルを当てる統計）と比べて精度を測れる | **上へ上げる・確認を足す方向にだけ使う。** Jev が「易しい」と言っても、`VIRTUAL_MARK.md` §3 と permissions の確認は外さない。取り消せない操作かどうかの判定はコードと人が行い、Jev に聞かない。Noul を多数並べると「はい」が出すぎる。作業の説明に私的情報を入れない。司令塔への助言で、Claude Code の中のモデル切替を Jev が直接行うのではない。まず影で 1 か月 |
| 4 | **Web の文に紛れた指示（プロンプト注入）の検出** | Noul「この文は人の読者ではなく AI への指示を含むか」「読み手の作業を変えようとしているか」 | ネットワークを開けて読む Web 文の追加の見張り。1 ページ約 $0.0004（1 万トークン。1 ドル 150 円なら約 0.06 円） | **防御の境界ではない**（公式・弱点 6）。既存の防御（データとして扱う・権限）を置き換えない。第三者の検証では、順位付けは良いが既定の 0.5 では攻撃の約 6 割しか拾わず、高い確信で誤る攻撃も報告がある。閾値を自前で決める。日本語のページは精度が下がる |

## 9. 評価の計画（`docs/eval-design.md` に反映）

- **版を固定してから**校正用の例を集める（`.env` の `JEV_MODEL=jev-1.13.0`）。版が変わったら閾値を測り直す
- 影ログに確信度と確率分布を残す（§10 で対応済み）。Noul の AUROC・Brier は以前から計算できたが、これで Choice・Score の多クラスの Brier と確信度の校正も計算できる
- **選択肢の並べ替え試験**: 校正用の各例で選択肢の順番を逆にしてもう 1 回聞き、答えが変わる割合を記録する（弱点 8）
- **言語の比較**: 同じ例を英語の原文と日本語訳で聞き、一致度の差を測る。問い（instructions・criteria）は英語で書く案と日本語で書く案を比べる。あわせて、Deußer らが公開した全応答から日本語（Belebele・SIB-200）の正解率を取り出す（費用 0）
- **罠問題**: 2 割に、本文への指示の埋め込み・自己申告を第三者評価に見せかけた文・「公式発表によれば」の偽装を入れる（弱点 6）
- **「該当なし」の試験**: 正解が選択肢に無い例を入れ、「不明」を選べる割合と、そのための閾値を測る
- 使い道 3（モデルの助言）は、escalations.log と費用台帳の「実際に足りたモデル」を正解として、影で 1 か月比べる
- 費用の見積もり: 1 回あたりの費用は入力トークン数 × $0.042/100 万（例: 1,200 トークンで約 $0.00005、2,500 トークンで約 $0.000105）。今の上限（1 日 60 回）で毎回 2,500 トークンなら約 $0.189/月（60 回 × 30 日 × $0.000105）。全件ふるいに広げる例: 1 日 100 本 × 4,000 トークンで約 $0.017/日（約 $0.504/月）。広げるには回数の上限を上げる必要があり、**支出が増えるので Mark の承認事項**

## 10. 実装への反映（2026-10-08）

**直した不具合: Jev の Score の答えを本番ではほぼ毎回捨てていた**（司令塔が直接修正。Codex はクラウド環境で使えないため。経緯は `HANDOVER.md`）
- なぜ起きたか: `orch/decisions.py` の `Score.coerce` は整数しか受け付けなかった。Jev の `score` は「段階番号 × 確率」の和で、1.43 のような小数になる（公式の API リファレンス）。テストは整数のモックで書いていたため通っていた。公式ドキュメントが読めず、二次情報から形を再構成していたのが元
- 何をしたか: 確率が最大の段階（同点は小さい番号）を答えにした。壊れた分布（全 0・合計のずれ・不正なキー）は次の手段へ落とす。確率の合計の許容幅は、小数第 2 位の丸めに合わせて `max(0.01, 0.005 × 段階の数)`。Jev が返す確信度・確率分布・score を `Decision.raw` と影ログ（`data/decisions_shadow.jsonl` の `jev`）に残す（キーは問いの選択肢・段階番号だけ、小数第 4 位、Choice は上位 5 件と残りの合計）。公式の応答の形をそのままテストに入れた
- 審査: Opus のコード審査 3 回目で APPROVE（1 回目 APPROVE の後、指摘の反映分を 2 回目で REJECT。重大 1＝確率の合計の許容幅を直した）
- 今後: 外部 API の答えの形は、一次資料の例をそのままテストに入れる。Mac で鍵を入れたら `python3 -m orch.decisions --demo --backend jev` で本物の形と確率の桁数を確かめる
- 決めていないこと: Score の確率が 2 つの段階で同点のとき、今は小さい番号を答えにする。「段階が高いほど危険」な止める側の問いでは止まらない側に倒れるので、評価セットで「最頻の段階・中央値の段階・期待値に最も近い段階」を比べてから決める（score と確率分布は影ログに残るので追加の費用は要らない）

**まだ直していない（必要になってから）**
- 選択肢の数の上限は 120 のまま（API は 255、事例集の 1 本は約 240 まで確実）。安全側なので変えない
- 429・529 の再試行はしない（判断層が Claude CLI → 既定値に落ちるので本流は止まらない）
- 判断層の呼び手が確信度で振り分けるのは、評価で閾値を決めてから

## 11. リスクと利益相反

- **宣伝と第三者の結果の食い違い**: 公式の事例集（§5）の数値はすべて自己申告で、比較の条件（素朴な LLM の使い方・測り方の違い・小さな自作データ）は TypeSafe に有利に働きうる。「193.6 倍速い・444.6 倍安い」は最も高い相手との比で、Vals も同じ桁を確認したが、安い LLM との差は数倍（§6.1）。「幻覚ゼロ」は型の保証の話で、正しさの保証ではない（公式ブログ自身が「経験的な数字ではない」と書く）
- **宣伝と注意書きの食い違い**: 用途の地図は「脱獄や注入を検出する万能の検証」とうたうが、弱点の一覧と RAG の事例は「敵対的な内容で答えが動く」「セキュリティ境界ではない」と書く。注意書きの方を採る
- **会社の若さと契約**: 公開から 3 週間、版は 1 つ、稼働率の約束なし、流量の上限は予告なく変わる。落ちても本流が止まらない今の判断層の形を保つ。契約とデータの扱いは §2 の表
- **版の移動**: `jev-latest` のままだと答えが黙って変わる（版の固定で防ぐ）
- **競合**: 同じ形の製品が速く出ている。判断層はベンダー非依存のまま保ち、Jev に固有の作りを広げない
- **証拠の若さ**: 第三者の評価のほとんどが未査読で、公開後 1〜3 週間のもの。2027-04 ごろに見直す

## 13. 用語

| 用語 | 意味 |
|---|---|
| 校正（キャリブレーション） | 「確率 0.8」と言った答えが、実際に約 8 割当たること |
| ECE | 校正のずれの大きさ。0 に近いほど確率どおりに当たる |
| Brier スコア | 確率の予測の誤差。0 に近いほど良い |
| AUC・AUROC | 正しいものを上に並べられるかの指標。1 が完璧、0.5 はでたらめ |
| κ（カッパ） | 2 つの判定の一致度から、偶然の一致を除いたもの |
| RMSE | 予測の誤差の大きさ |
| BM25 | 単語の重なりで文書を探す昔ながらの検索の方式 |
| CatBoost | 表のデータを学習する普通の機械学習の道具 |
| LegalBench・MMLU・Belebele | 法律の推論・幅広い知識・多言語の読解の試験問題集 |
| 10-K | 米国の上場企業の年次報告書 |
| RLHF・RLVR・RLCD | 人の好みで鍛える・答えを検証できる課題で鍛える・確率が当たるように鍛える学習法 |
| MCA・DPA | TypeSafe との基本契約・データ処理の契約 |
| SLA | 稼働率などの約束。破ると返金などがある |
| Goodhart の法則 | 点数を目標にすると、点数が当てにならなくなること |
| ゼロショット | 例を見せずに、問いだけで答えさせること |
| t=0（温度 0） | LLM の答えの揺らぎを最も小さくする設定 |
| logprob | LLM が各単語に付ける確率。答えの確信度の代わりに使える |
| micro-F1 | 見落としと誤検出の両方を考えた正解率の一種 |
| fail-closed | 審査できないときは「不合格」の側に倒すこと |
