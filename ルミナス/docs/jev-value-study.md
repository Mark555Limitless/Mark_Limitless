# Jev（TypeSafe の System One）の利用価値の調査 v0.1

> 2026-10-08、Mark の依頼「Jev の利用価値を広く深く探って学習してください」で調査した。
> ネットワークを一時的に Full にして、公式ドキュメント（docs.typesafe.ai の全ページの一括版 `llms-full.txt`）を直接読んだ。
> 事例集 18 本の読み込みと第三者の評価の調査は、サブエージェント（Sonnet）2 体に分けた。
> 出典の信頼度は ①〜⑤（CLAUDE.md）。TypeSafe 自身の数値はすべて〔自己申告〕で、第三者の再現は見つかっていない（§6）。

## 0. 結論

1. **Jev は「判断の部品」で、文章を書く AI ではない。** 文書（state）と型のある問い（Choice・Score・Noul）を渡すと、約 0.1 秒で確率つきの答えを返す。生成・要約・計算・日付の比較はできない。
2. **はっきりした強みは速さと安さ。** 1 回 約 0.1 秒・約 $0.00005 で、小さな LLM（Haiku 4.5・GPT-5.4 mini）より 7〜34 倍速く 20〜76 倍安い〔自己申告〕。精度で LLM に勝つことは、独立には示されていない。
3. **価値が出る使い方は「大量の安い一次ふるい」と「確信度で人や上位モデルへ回す仕組み」。** 最終判断や安全の境界には使えない（公式も「セキュリティ境界ではない」と書いている）。
4. **日本語は弱い。** 公式に「英語が主。CJK も扱えるが同じ精度ではない」とある。問いは英語で書き、日本語の文書は別に測ってから使う。
5. **ルミナスでの第一候補は 3 つ:** ①出典の種類（一次情報・自己申告・噂）を見分ける「止める信号」、②引用が主張を裏付けるかの検査、③作業を最安で足りるモデルへ振り分ける助言（好み [1] の自動エスカレーション）。どれも影ログで測ってから使う。
6. **実装の不具合を 1 件見つけて直した**（§10）。Jev の Score の答えを、本番ではほぼ毎回「形式不正」として捨てていた。

## 1. Jev とは何か（一次情報①）

- TypeSafe の主力モデルで、最初の「System One」モデル。名前はカーネマンの「速い思考（システム1）」から
- LLM と同じく自然言語を理解するが、**文章を生成しない**。答えは型のある値と確率だけ
- 学習法は RLCD（Reinforcement Learning for Calibrated Decisions）。人の好み（RLHF）でも検証できる報酬（RLVR）でもなく、「確率が当たる割合と一致する（校正）」ことを目標にする。共同創業者の Diogo Almeida は RLHF の共同発明者と公式は書いている
- 1 回の呼び出しで、1 つの state に多数の問いを並列・独立に当てる。問いを増やしても応答時間はほとんど伸びず、問い同士が影響しない（文脈の劣化が起きない）
- 全利用者が同じ重みを使う。顧客データでの追加学習（fine-tune・LoRA）はない。自社の知識は state に、規則は問いの `instructions`・`criteria` に入れる
- Claude Code や Codex の中身として差し替えるものではない（公式「Jev with coding agents」）。エージェントが書くコードの中で、判断の部品として呼ぶ

### 3 つの問いの型

| 型 | 聞くこと | 返るもの | 上限 |
|---|---|---|---|
| Choice | 選択肢から 1 つ選ぶ | `choice`・各選択肢の `probabilities`・`confidence` | 選択肢 255 個（事例集の 1 本は「約 240 まで確実」） |
| Score | 段階の尺度で採点 | `score`（段階番号×確率の和。例 1.43）・`legend`・`probabilities`・`confidence` | 段階 2〜10（11 はサーバーエラー） |
| Noul | 文が真かどうか | `noul`（0〜1） | 確信度は返らない。公式の換算は \|2p−1\| |

## 3. 確信度の仕組み（一次情報①）

- Choice: (p_max − 1/n) ÷ (1 − 1/n)。均等なら 0、1 つに集中なら 1。上位 1 つしか見ないので (0.6, 0.3, 0.1) も (0.6, 0.2, 0.2) も 0.4
- Score: 最も確からしい段階からの「確率で重み付けした距離」を、均等な場合の距離で割って 1 から引く。隣の段階に割れるより、両端に割れるほうが低くなる
- Noul: 確信度はなく、0.5 に近いほど不確か。換算するなら \|2p−1\|
- 公式は、上位の確率そのものと「1 位 ÷ 2 位」の比も実用的だとしている
- 使い方の基本は 3 段: **高い → 自動で進む／中 → 確認か上位へ／低い → 動かない（人・別の仕組みへ）**。閾値は操作の重さで変える（読むだけの操作は低く、取り消せない操作は高く）
- 校正は「多数の予測の集まり」での性質で、個々の答えの正しさは保証しない（公式の注意）
- 公式は「校正されている」と書くが、**校正の測定値（信頼度図・ECE・Brier）は公開資料に見当たらない**。確信度で分けた正解率の差の例（SEC の業種分類で、確信度 0.9 以上が 27/30 正解、未満が 12/30）が近い根拠〔自己申告〕

## 4. 既知の弱点（公式「Jev 1.13 jaggedness」、2026-10-02 版①）

| # | 弱点 | 公式の対策 | ルミナスでの注意 |
|---|---|---|---|
| 1 | 字義どおりに読む（否定・範囲の言葉を額面どおり） | 条件と境界の例を criteria に書く | 問いは短く直接に |
| 2 | 計算・数えること・数値の近さ | コードで計算する | **ベンチマークの数値の比較はコードで**行い、Jev に聞かない |
| 3 | 日付の前後・間隔 | 年月日を Choice で取り出し、比較はコード | 発表日・論文の版の新旧はコードで |
| 4 | 二重否定・何段もの参照 | 参照を減らし、state の該当箇所を名指し | |
| 5 | 無関係な内容が多い大きな state | 先に絞って必要な部分だけ送る | 記事全文ではなく該当段落を送る |
| 6 | **敵対的な内容**（埋め込まれた指示・誤誘導・自分の分類を主張する文） | criteria を明確にし、配備前に試す | **注入された文で答えが動く。** 止める信号には使えても、通す判断の根拠にしない |
| 7 | instructions と criteria の矛盾 | 両者をそろえる | 「真＝いいえ」のような逆の Noul を作らない |
| 8 | **Choice の選択肢の順番**（先頭に寄る） | 並べ替えて答えが変わらないか確かめる | 評価で並べ替え試験をする（§9） |
| 9 | 文章の生成 | 生成モデルを使う | 抽出は「候補を正規表現か LLM で出し、Jev が選ぶ」 |

## 5. 公式の事例集から分かること（18 本、すべて〔自己申告〕）

| 事例 | 中身 | 主な数値〔自己申告〕 | 読み取りの注意（所見） |
|---|---|---|---|
| 自己一貫性（Choice 8 問 × 15 回） | 境界的な投稿の審査 | 同じラベルを返す割合 90.8%（LLM 87.5〜100%）。8 問中 2 問でラベルが割れた | Haiku t=0 の方が安定（100%）。精度は測っていない |
| 自己一貫性（Noul 14 問 × 15 回） | 保険請求の振り分け | 確率の標準偏差 0.0102。0.5 をまたいで揺れた問いが 1 つ | LLM 側の数値は本文に無い |
| 問いをまとめる | 5 万 4 千字の文書に 13 問 | 1 回 $0.000497・0.27 秒、13 回に分けると 12.2 倍高く 10.0 倍遅い | 分けた側は逐次実行の合計 |
| 再ランク | 判例検索（BM25 の上位 30 件） | Top1 5%→18%、Top10 38%→62%。1,200 回で $0.0645 | 比較は BM25 だけ。40 問 |
| スキル提案 | エージェントの 182 スキルから 1 つ提案 | 誤ったスキルの読み込み 16.8%→7.3%、不要な読み込み 9.8%→4.0%。315 件中 37 件改善・7 件悪化 | 依頼文の半分は Sonnet が作った易しいもの |
| 引用の検査 | LLM の引用が裏付けか・矛盾か・無関係か | 仕込んだ誤り 4 件をすべて検出（2 件は人への回付で） | 8 件の自作 |
| RAG の仕分け | 関連・証拠・前提との矛盾・注入 | 注入入りの文を 0.99 で除外 | 公式自身が「セキュリティ境界ではない」 |
| ガードレール | 脱獄・有害依頼・医療助言・自傷 | 有名な脱獄の 1 つは 0.74（閾値 0.70 すれすれ） | 15 件。誤検知率は未測定 |
| 抽出の段階分け | 小モデルで抽出→Jev で検証→怪しいものだけ大モデル | 図の上では、同じ費用なら単独のモデルより品質がやや高い（読み取りの近似。例: 約 0.79 を約 $0.02 で。単独の GPT-5.5 は約 0.78 を約 $0.025） | 図は過去版・判定者が曖昧・本文と図の費用が不一致・誤差の幅が重なる |
| 確信度で粒度を変える | SEC の 10-K を 75 業種に | 確信度 0.9 以上 27/30 正解、未満 12/30。未満を上位 10 区分に上げると 48/60 が使える答え | 閾値を同じデータで決めている |
| 特徴量の発見 | ワイン評の点数予測（2,000 件） | 38 問の答えを CatBoost に入れ RMSE 3.09→1.77 | 1 データセット |

- 比較の公平性: LLM 側は 1 本のゼロショットで確率を数値で言わせる素朴な形（logprob・少数例・構造化出力なし）。速度は LLM を 16 並列、TypeSafe を逐次で測っている。比較相手は 2025〜26 年前半の小型・推論モデル
- 「100 倍安い」（用途の地図ページ）は、小型モデル比 20〜76 倍と推論モデル比 620〜900 倍の間。根拠のない丸めた宣伝の数字として扱う
- 全事例が英語のデータ。日本語の例は 1 つもない

## 7. 得意・不得意のまとめ

**向く仕事**
1. 決まった観点での一括判定（1 文書に十数問）
2. 確率で「自動・人・止める」に振り分ける仕事（審査・トリアージ・ガードレール・引用の検査）
3. 閉じた選択肢から選ぶ仕事（分類・振り分け・候補からの抽出・階層分類）
4. 高いモデルの前の安いふるい（怪しいものだけ上位へ）
5. 意味の判定を数値の特徴量にして、普通の機械学習に渡す仕事

**向かない仕事**
1. 文章の生成・要約・翻訳
2. 計算・数の比較・日付の比較・数えること
3. 候補を前もって用意できない抽出、255 を超える選択肢
4. 安全の境界、正しさの保証（注入で動く・閾値の近くで答えが割れる）
5. 何段もの推論が要る判断（System 2 の仕事は Claude へ）
6. 日本語が中心の判断（自前で測るまで）

## 8. ルミナスと AI NEWS Select での使い道（優先順）

前提: Jev は助言で、**止める側の信号から使う**（`docs/eval-design.md`）。通す判断・取り消せない操作の承認には使わない（CLAUDE.md 不変条件 1）。送るのは「公開可」の内容だけ（`docs/support-ai.md` §7）。

| 順 | 使い道 | 問いの形（例） | 価値 | 注意 |
|---|---|---|---|---|
| 1 | **出典の種類の判定**（好み [3] の信頼度ピラミッドと利益相反） | Choice「この数値を測ったのは誰か」{開発元の自己申告・第三者評価機関・査読論文・不明}。Choice「この記事の主張の出どころ」{公式発表・査読/会議・一次情報を引いた報道・匿名情報源や噂・不明} | 自己申告のベンチマークや噂の段階の記事を、安く全件ふるえる。止める側の信号にちょうどよい | ドメインで決まる部分（公式ドメイン・査読誌・通信社）はコードの表で先に決める。Jev は URL を開けず、本文の主張だけで判定する。「公式発表によれば」と書くだけで寄る（罠問題で測る） |
| 2 | **引用・要約が一次情報を裏付けるかの検査** | Choice「この段落はこの主張を」{裏付ける・矛盾する・何も言っていない}。数値はコードで正規表現で取り出して突き合わせる | 好み [3]「論文の要旨・数値・結論を直接確認し報道の要約と照合」の機械化。裏付けがない・矛盾するものだけ Claude に回す | 公式の事例は 8 件だけ。言い換えた引用は文字列照合で落ちるので、あいまい照合が要る |
| 3 | **最安で足りるモデルへの振り分けの助言**（好み [1]） | 作業の説明を state に、Noul を数問（「複数ファイルにまたがる変更か」「Web の一次情報の確認が要るか」「取り消せない操作を含むか」「判断に迷う論点があるか」）。段階はコードで合成 | 約 0.1 秒・ほぼ無料で、毎回の作業に「どのモデルから始めるか」の根拠を付けられる。月 1 回の escalations.log の監査と比べて精度を測れる（§9 の実験 A） | 作業の説明に私的情報を入れない。Claude Code の中のモデル切替を Jev が直接行うのではなく、司令塔への助言。まず影で 1 か月 |
| 4 | **Web の文に紛れた指示（プロンプト注入）の検出** | Noul「この文は人の読者ではなく AI への指示を含むか」「読み手の作業を変えようとしているか」 | Full のネットワークで読む Web 文の追加の見張り。1 ページ 1 円未満 | **防御の境界ではない**（公式・弱点 6）。既存の防御（データとして扱う・権限）を置き換えない。日本語のページは精度が下がる |
| 5 | 重複・同一話題の判定 | 既存（AI NEWS Select で稼働中。κ 0.54、補正後 約 0.69） | 原本で実績あり | 原本の設定は変えない |
| 6 | 文書の決まりの点検（意味の lint） | Noul「この数値に出典が付いているか」「自己申告の数値に『自己申告』と書いてあるか」 | digest・HANDOVER・投稿案の規則違反を安く見つける | 日本語の文書なので、まず精度を測る |
| 7 | 審査の点数の補助 | 使わない | | 審査は fail-closed。Jev の点数で通さない（Goodhart の循環） |

## 9. 評価の計画（`docs/eval-design.md` に反映）

- 版を固定する: `.env` の `JEV_MODEL=jev-1.13.0`（別名は新版で動く）。版が変わったら閾値を測り直す
- 影ログに確信度と確率分布を残す（§10 で対応済み）。Noul の AUROC・Brier は以前から計算できたが、これで Choice・Score の多クラスの Brier と確信度の校正も計算できる
- **選択肢の並べ替え試験**: 校正用の各例で選択肢の順番を逆にしてもう 1 回聞き、答えが変わる割合を記録する（弱点 8）
- **言語の比較**: 同じ例を英語の原文と日本語訳で聞き、一致度の差を測る。問い（instructions・criteria）は英語で書く案と日本語で書く案を比べる
- **罠問題**: 2 割に、本文への指示の埋め込み・自己申告を第三者評価に見せかけた文・「公式発表によれば」の偽装を入れる（弱点 6）
- 使い道 3（モデルの振り分け）は、escalations.log と費用台帳の「実際に足りたモデル」を正解として、影で 1 か月比べる
- 費用の見積もり: 1 回 2,500 トークンなら約 $0.000105。今の上限（1 日 60 回・月 $1）では回数の上限が先に効き、月 $0.2 程度。全件ふるいに広げるなら回数の上限を上げる必要がある（**支出が増えるので Mark の承認事項**。それでも月数ドルの見込み）

## 10. 実装への反映（2026-10-08）

**直した不具合: Jev の Score の答えを本番では毎回捨てていた**
- なぜ起きたか: `orch/decisions.py` の `Score.coerce` は整数しか受け付けなかった。Jev の `score` は「段階番号 × 確率」の和で、1.43 のような小数になる（公式の API リファレンス）。テストは `"score": 2` という整数のモックで書いていたため通っていた。公式ドキュメントが遮断で読めず、二次情報から形を再構成していたのが元
- 何をしたか: `probabilities` があれば確率が最大の段階（同点は小さい番号）を答えにした。キーが段階番号でない・確率でない値がある・全部 0・合計が 1 から外れている分布は、壊れた答えとして従来どおり次の手段へ落とす。あわせて、Jev が返す確信度・確率分布・score を捨てずに `Decision.raw` と影ログ（`data/decisions_shadow.jsonl` の `jev`）に残すようにした。影ログが 5MB の打ち切りにすぐ届かないよう、確率のキーは問いの選択肢・段階番号だけ、値は小数第 4 位、Choice は上位 5 件と残りの合計にした。Noul は answers の値がそのまま確率なので何も足さない（確信度が要れば \|2p−1\|）。公式の応答の形をそのまま使ったテストを足した
- 審査: Opus のコード審査で APPROVE。軽 3 点（壊れた分布・影ログの肥大と任意のキー・Noul の確信度の混同）と任意の指摘（桁の大きい整数で OverflowError・テストの欠け）も反映した
- 今後: 外部 API の答えの形は、一次資料の例をそのままテストに入れる。Mac で鍵を入れたら `python3 -m orch.decisions --demo --backend jev` で本物の形を確かめる
- 決めていないこと: Score の確率が 2 つの段階で同点のとき、今は小さい番号を答えにする。「段階が高いほど危険」な止める側の問いでは止まらない側に倒れるので、評価セットで「最頻の段階・中央値の段階・期待値に最も近い段階」を比べてから決める（score と確率分布は影ログに残るので追加の費用は要らない）

**まだ直していない（必要になってから）**
- 選択肢の数の上限は 120 のまま（API は 255、事例集の 1 本は約 240 まで確実）。安全側なので変えない
- 429・529 の再試行はしない（判断層が Claude CLI → 既定値に落ちるので本流は止まらない）
- 判断層の呼び手が確信度で振り分けるのは、評価で閾値を決めてから

## 11. リスクと利益相反

- 数値はすべて TypeSafe の自己申告。比較の条件（素朴な LLM の使い方・測り方の違い・小さな自作データ）は TypeSafe に有利に働きうる
- 宣伝と注意書きの食い違い: 用途の地図は「脱獄や注入を検出する万能の検証」とうたうが、弱点の一覧と RAG の事例は「敵対的な内容で答えが動く」「セキュリティ境界ではない」と書く。注意書きの方を採る
- 流量の上限が予告なく変わる。自動実行に組み込むときは、落ちても本流が止まらない形（今の判断層）を保つ
- 版が `jev-latest` のまま動くと、答えが黙って変わる（版の固定で防ぐ）
- データの扱い: 学習に使わないのは自己申告。保持期間と再委託先は DPA の精読が要る（`docs/support-ai.md` §6 の表）
