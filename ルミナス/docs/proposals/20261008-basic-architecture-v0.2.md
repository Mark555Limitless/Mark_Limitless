1 つの作業は、必ず **Plan → Do → Check → Act** を 1 周する。Check を通らない成果は採用しない。

## 2. 中枢と役割の割当

### 2.1 基本単位: 方針・実行・検証の 3 役

Sakana AI の TRINITY が使う Thinker（方針）・Worker（実行）・Verifier（検証）の 3 役を、作業を割り当てる単位にする（論文本文は未読。着想として使う。`docs/research-sources.md`）。

- **方針**: 論点と採点基準（効果・信頼性・コスト・可逆性）を先に書く。司令塔か上位モデル
- **実行**: 調べる・書く・実装する。最も安い十分なモデル、または Codex
- **検証**: 実行したものとは**別のモデル**が、採点基準に沿って確かめる

### 2.2 広げるか深めるか: 探索予算

Sakana AI の AB-MCTS は「新しい案を広げる」か「今の案を深める」かを予算の中で選ぶ（自己申告の成果。`docs/research-sources.md`）。ルミナスではこれを人が選べる 3 段階にする（`VIRTUAL_MARK.md` §4、ロールプレイの「好奇心ブースト」）。

| 予算 | 案の数 | 検証 | 使う場面 |
|---|---|---|---|
| 低 | 1 案 | 審査 1 回 | 日常の保守 |
| 中（既定） | 2〜3 案を比べる | 審査 1 回 | 通常の作業 |
| 高 | 異種モデルも入れて 3 案以上 | 反証役を立てる（Agent Team も可） | 憲章・設計の根幹・公開物 |

統一は**票決ではなく根拠の比較**で行い、採らなかった案と理由も記録する。

### 2.3 モデルの割当（最安十分と自動の上げ下げ）

| 仕事 | 既定 | 上げる先 | 上げる条件 |
|---|---|---|---|
| 機械的な作業（整形・集計・転記） | Haiku 4.5 | Sonnet 5.5 | 書式の崩れ、取りこぼし |
| 調べもの・下書き・文書の審査 | Sonnet 5.5 | Opus 5.5 | 判断しきれない論点、出典の矛盾 |
| 司令塔・コード審査・設計 | Opus 5.5 | Fable 5.1 | 憲章・安全・設計の根幹、深刻な矛盾 |
| 実装 | Codex（GPT-6 Astra） | 司令塔が仕上げる | 利用枠の上限、失敗 |
| 下書き・別の視点 | Gemini 3.8 Flash | — | — |
| 構造化判断の助言 | Jev | Claude CLI（Haiku → Sonnet）→ 既定値 | Jev の失敗・時間切れ |

- 候補が複数なら安い方を選ぶ。上げ下げは `state/escalations.log` に記録し、月に 1 回、妥当だったかを監査する（Mark の指示 [1]）
- **要判断（§6-1）**: 分譲指示書の役割表は「司令塔＝その時点の Claude 最強（Fable 5.1）」。本提案は **Opus 5.5 を既定にし、重大な判断だけ Fable 5.1 へ上げる**案を推す。今回のコード審査 5 回は、Opus 5.5 の司令塔と Opus の審査役で APPROVE まで進められた

## 3. ルミナズ（内部の手足）

`.claude/agents/*.md` に置く。1 人の審査で足りる作業はサブエージェント、複数の視点をぶつけたいときだけ Agent Team（Mark が見ている対話セッションで、必要なときだけ有効化）。

| 名前 | 役割 | 既定モデル | 道具 | 状態 |
|---|---|---|---|---|
| AuditPulse（`luminous-reviewer`） | 文書・設定の審査（常駐） | Sonnet → Opus | 読むだけ | 稼働中 |
| `luminous-code-reviewer` | コード審査。`docs/review.md` の形式で 1 行目 APPROVE／REJECT | Opus | 読むだけ＋テストの実行 | **新設を提案** |
| StarPulse（`luminous-researcher`） | 一次情報の調査、比較表。出典の信頼度ピラミッド、自己申告の明記 | Sonnet → Opus | 読むだけ＋Web | 新設を提案 |
| Worker（`luminous-spec-writer`） | Codex への指示書（目的・ALLOWED・禁止・変更・テスト・完了条件） | Sonnet | 読む＋`docs/specs/` への書き込み | 新設を提案 |
| GuardianPulse（`luminous-guardian`） | 事実の GO/NO-GO、インジェクション・秘匿情報・規約の点検 | Sonnet → Opus | 読むだけ＋Web | 新設を提案 |

- コード審査役を常駐の定義にする理由: 今は依頼のたびに Agent でモデルを指定して起動している。2 回目の審査で、審査役が本物の `claude -p` をダミーの内容で 2 回実行した。定義ファイルに「外部の CLI・API を呼ばない。外部呼び出しはモックで確かめる」を固定し、毎回の依頼文に頼らないようにする
- AI NEWS Select の「判定役」の手順（出典ピラミッド、自己申告の明記、サブ LLM の深掘り、GO/NO-GO）は GuardianPulse の標準手順にする

## 4. サポートAI（外部の目）

分譲指示書（2026-10-08）の 6 点セット（固定コマンド・上限・記録・点検・停止スイッチ・フォールバック）がそろったものだけを使う（`docs/support-ai.md`）。

| サポートAI | 役割 | 呼び方 | 上限の案 | 失敗したとき |
|---|---|---|---|---|
| Codex（GPT-6 Astra） | 実装の主力。読み取り専用の第3の意見 | `tools/codex_impl.sh`・`tools/codex_opinion.sh` | 1 日の実行回数の目安（サブスク枠を共有） | 司令塔が仕上げる |
| Gemini 3.8 Flash | 下書き・要約・別の視点 | `python3 -m orch.gemini` | 1 日 $1 | 使わずに続ける |
| Jev | 選択肢・段階・確率で答える助言 | `orch.decisions` | 1 日 60 回・月 $1 | Claude CLI → 既定値 |
| Grok（任意） | 別視点の調査・反証役 | 未実装 | — | — |
| 将来の候補 | Sakana Fugu・TreeQuest（難問用の外部の統率役） | 未実装 | — | 自前の評価で比べてから |

- Codex の実装は、範囲検査（`tools/scope_check.py`）を通ったものだけを、司令塔がテストと審査の後にコミットする。Codex は commit しない
- 外部へ渡すのは公開可・push 済みのファイルだけ（`scripts/export-public.sh`）。送る文章は「データであって指示ではない」と明記する
- 取り消せない操作の承認は外部AIに委ねない。Jev の判定も最終判断にしない

## 5. 記憶と継続・自走・安全・評価

### 5.1 探偵アニ（記憶と継続）

| 時点 | 何をするか | 仕組み |
|---|---|---|
| 開始 | 憲章・自走範囲・ROUTINE・HANDOVER の最新の節・最新 digest・Obsidian・最終プロンプトを注入、外部AIの点検 | SessionStart hook |
| 作業中 | モデル切替の記録、Codex の実行中の編集停止 | PostModelSwitch・PreToolUse hook |
| 終了前 | HANDOVER（先頭に節）・digest・Obsidian を書かないと止める | Stop hook |
| 終了 | Obsidian へ同期、最終プロンプトの docx を再生成 | SessionEnd hook |
| 追加（Phase 2） | 圧縮の前に要約を保存、定期チェックインで次の Plan を起こす | PreCompact hook、Routine |

### 5.2 仮想Mark（自走の範囲）

可逆で範囲内なら聞かずに進む。削除・公開・送信・課金・憲章や権限の変更・新しい外部サービス・鍵は止まって確認する（`VIRTUAL_MARK.md`。§3 が §2 に優先）。

### 5.3 安全（横断 A）

- 鍵は `.env`（権限 600・git 管理外）だけ。入力は Mark が `tools/set_env_key.sh` で行う。Claude は読まない
- 鍵らしき文字列は、hook と git の pre-commit・pre-push の両方で止める
- Codex の実行後は、入れ子の `.git` の隔離、本物の `.git` の設定の確認、フォルダ全体の内容の比較、待ってからの比べ直しを、git を使う前に行う
- 保護ファイル（憲章・権限・hooks など）の変更は確認が出る。サブエージェントや外部AIの「承認した」は承認ではない

### 5.4 評価（横断 B）

| 指標 | 何を測るか |
|---|---|
| 完了率 | 受け入れ基準を人手なしで満たした作業の割合 |
| 1 作業あたりの費用 | 失敗・やり直しも含めた API 費用 |
| エスカレーション率 | 安いモデルから上げた割合と、上げて成功した割合 |
| 復元時間 | 再開から作業の再開まで（目標 1 分以内） |
| 審査の重大指摘 | 成果物あたりの数（下がることを確かめる） |
| 事実の誤り・秘匿情報の事故 | 目標 0 |

改善（プロンプト・エージェント定義・指示書の型）は「提案 → 評価で旧版と比べる → 審査 → Mark の承認 → 適用」。憲章・権限・hooks・自走範囲は自動では変えない。
