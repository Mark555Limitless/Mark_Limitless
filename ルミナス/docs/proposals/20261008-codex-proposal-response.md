## 0. 結論

1. **大筋で賛成する。** 二つの案は同じ方向を向いている。使命と方針を外に保存して計画役を交換できるようにする、最安で足りるモデルから始めて検証で上げる、外部AIは助言で最終判断は持たせない、測っていない数字を実績にしない、の 4 点は一致している。
2. **Codex 案は、Claude 案の弱いところを正しく突いている。** いちばん大きいのは「実行の制御を、計画するモデルから独立させる」こと。Claude 案は安全を hooks・ラッパー・上限に分けて持たせているが、全体を止める一つのスイッチも、外部操作の状態も、予算の予約もない。ここは Codex 案を採る。
3. **ただし、作り始める順番は Claude 案に寄せたい。** Mac 上の常駐の管理プロセスと SQLite は、Phase 1 では早い。今のファイルと hooks で測ってから、足りない所だけを作る。
4. **Codex は、AI NEWS Select の原本に Jev の不具合があることを独立に見つけていた。** 今日ルミナスで直した Score の不具合（小数の答えを整数しか受け付けず捨てる）と同じもの。原本はルミナスから直さない決まりなので、Fable5 の司令塔に伝えることを勧める（§5）。

## 3. 慎重にしたい点・違う意見

1. **常駐の管理プロセスと SQLite は、Phase 1 では早い。**
   - 理由 1: 保守するのは Claude と Codex で、Mark はエンジニアではない。動くプロセスが 1 つ増えると、止まった・二重に動いた・状態が壊れたを Mark が見分けられない
   - 理由 2: 今の作業量（1 日に数件、外部AIの呼び出しは 1 日数十回）なら、jsonl の台帳・ロック・hooks で足りている。足りないのは §2 の A と D で、どちらもファイルで作れる
   - 提案: Phase 1 はファイルのまま A・D・E を入れる。Phase 2 の終わりに「並列の数・待ち行列の長さ・状態の食い違いの件数」を測り、ファイルで足りなくなったら管理プロセスを作る（Codex 案の §5 と同じ形で）
2. **「実行制御」を 1 つの構成要素として独立させるのには賛成。** Claude 案では「横断 A: 安全」に混ざっている。構成を「統治・中枢・実行制御・ルミナズ・サポートAI・記憶と継続・自走の範囲」と「評価」に組み直すのがよい（§4）。ただし今の実体は「hooks・ラッパー・上限・停止の印」の集まりで、プロセスではない、と明記する
3. **鍵の控えは Codex 案が正しい。** 今は `tools/set_env_key.sh` が、鍵を書き換えるたびに `.env` の写しを非公開フォルダ（`ルミナス_非公開/env_backups/`）へ平文で残す。写しは回数分増える。macOS のキーチェーン（またはパスワード管理アプリ）に控えを置き、平文の写しは作らない方がよい。PW Checker の登録の見直しも要るので、Mark の判断事項にする（§6-2）
4. **共通ルールの正典を 1 つにする案に賛成。ただし置き場所はこのリポジトリに。** Codex 案は `governance/COMMON_RULES.md` を正典にし、`CLAUDE.md`・`AGENTS.md` を薄い入口にする。今は `CLAUDE.md` と `AGENTS.md` が別々に規則を持ち、食い違うおそれがある。Mac の提案フォルダの `COMMON_RULES.md` と `architecture-reviewer.md` をこのリポジトリに取り込み、`CLAUDE.md` と照らし合わせてから決めたい（このリポジトリには無いので、Mark に渡してもらう必要がある）。Obsidian に別の写しを手で持つのは、Codex 案自身が言うとおり食い違いの元なので、Obsidian は同期先（読むだけ）にする
5. **「仮想Mark の推測で範囲は広がらない」に賛成。** `VIRTUAL_MARK.md` も同じ考え（§3 が §2 に優先）。Codex 案の「公開・送信・課金も、個別に許可範囲があればその中で自走できる」は、今の憲章（取り消せない操作は止まって確認）より広い。広げるかどうかは Mark の判断で、今は広げない
6. **Sakana の扱いは一致。** Fugu の性能は自己申告で、学習済みの指揮役を再現したとは言わない。TreeQuest（AB-MCTS）は、正解判定やテストがある難しい課題だけに後で入れる、に賛成（Claude 案の探索予算「高」の中身として）

## 5. Codex の調査で分かった、原本（AI NEWS Select）の問題

- **Jev の Score**: 原本の判断層も、Jev の小数の答えを整数しか受け付けない形らしい（Codex の静的調査。「ローカル文書に小数の実応答が記録」とある）。ルミナスでは今日直した（`docs/jev-value-study.md` §10、コミット a1e7102・b4c679d）。原本で Score を使っていれば、その答えは毎回 Claude に回るか既定値になっている
- **Codex の再試行**: 原本のラッパーは失敗（0 以外の終了）すると同じ作業領域で再試行する（Codex の静的調査）。途中の変更が重なるおそれ。ルミナスの版は「失敗かつ無変更のときだけ、別のモデルで 1 回」にしてある
- **ルミナスからは直さない**（不変条件 6）。Mark から Fable5 の司令塔に、ルミナスの修正（`orch/decisions.py` の `_top_level` とテスト）を参考として伝えることを勧める

## 6. Mark に決めてほしいこと（Claude 案 §6 の 8 点に追加）

1. **実行制御を独立の構成要素にするか**（推奨: する。Phase 1 は全体の停止スイッチ・失敗の種類の表・評価の版だけをファイルで。管理プロセスと SQLite は Phase 2 の終わりに実測で決める）
2. **鍵の控えの置き場**（推奨: 平文の `.env` の写しをやめ、macOS のキーチェーンかパスワード管理アプリへ。`tools/set_env_key.sh` の変更は指示書 → Codex → 審査で。PW Checker の登録の見直しは Mark か Fable5 の司令塔）
3. **共通ルールの正典を 1 つにするか**（推奨: する。Codex の `COMMON_RULES.md` と `architecture-reviewer.md` を渡してもらい、`CLAUDE.md` と照合してから決める）
4. **原本の Jev Score と Codex の再試行を Fable5 の司令塔に伝えるか**（推奨: 伝える）
5. **自走の範囲を広げるか**（Codex 案は「個別の許可範囲があれば公開・送信・課金も自走」。推奨: 今は広げない）
