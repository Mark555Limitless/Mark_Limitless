## 0. 結論

1. **大筋で賛成する。** 二つの案は同じ方向を向いている。使命と方針を外に保存して計画役を交換できるようにする、最安で足りるモデルから始めて検証で上げる、外部AIは助言で最終判断は持たせない、測っていない数字を実績にしない、の 4 点は一致している。
2. **Codex 案は、Claude 案の弱いところを正しく突いている。** いちばん大きいのは「実行の制御を、計画するモデルから独立させる」こと。Claude 案は安全を hooks・ラッパー・上限に分けて持たせているが、全体を止める一つのスイッチも、外部操作の状態も、予算の予約もない。ここは Codex 案を採る。
3. **ただし、作り始める順番は Claude 案に寄せたい。** Mac 上の常駐の管理プロセスと SQLite は、Phase 1 では早い。今のファイルと hooks で測ってから、足りない所だけを作る。
4. **Codex は、AI NEWS Select の原本の Jev の扱いに、今日ルミナスで直したのと同じ形の問題を見つけていた**（Score の小数の答えを、整数しか受け付けない対応付け）。原本が Score を使っていれば同じ不具合になりうる。原本はルミナスから直さない決まりなので、Fable5 の司令塔に、修正の参考を渡して Score を使っているかの確認を頼むことを勧める（§5）。

## 3. 慎重にしたい点・違う意見

1. **常駐の管理プロセスと SQLite は、Phase 1 では早い。**
   - 理由 1: 保守するのは Claude と Codex で、Mark はエンジニアではない。動くプロセスが 1 つ増えると、止まった・二重に動いた・状態が壊れたを Mark が見分けられない
   - 理由 2: 外部AIの呼び出しは上限（Jev は 1 日 60 回、Gemini は 1 日の費用の上限）で抑えてあり、実際の呼び出しはまだ 0 件（鍵が未設定）。この規模なら記録のファイル（jsonl）・ロック・hooks で足りる見込み。足りないのは §2 の A と D で、どちらもファイルで作れる
   - 提案: Phase 1 はファイルのまま A・D・E を入れる。Phase 1 の評価で件数・並列の数・待ち行列の長さ・状態の食い違いの件数を測り、ファイルで足りないと分かったら Phase 2 の終わりに管理プロセスを作る（Codex 案の §5 と同じ形で）
2. **「実行制御」を 1 つの構成要素として独立させるのには賛成。** Claude 案では「横断 A: 安全」に混ざっている。構成を「統治（自走の範囲を含む）・中枢・実行制御・ルミナズ・サポートAI・記憶と継続」の 6 つと「評価と改善」に組み直すのがよい（§4）。ただし今の実体は「hooks・ラッパー・上限・停止の印」の集まりで、プロセスではない、と明記する
3. **鍵の控えは Codex 案が正しい。** 今は `tools/set_env_key.sh` が、鍵を書き換えるたびに `.env` の写しを非公開フォルダの控え用の場所へ平文で残す。写しは回数分増える。macOS のキーチェーン（またはパスワード管理アプリ）に控えを置き、平文の写しは作らない方がよい。PW Checker の登録の見直しも要るので、Mark の判断事項にする（§6-2）
4. **共通ルールの正典を 1 つにする案に賛成。ただし置き場所はこのリポジトリに。** Codex 案は `governance/COMMON_RULES.md` を正典にし、`CLAUDE.md`・`AGENTS.md` を薄い入口にする。今は `CLAUDE.md` と `AGENTS.md` が別々に規則を持ち、食い違うおそれがある。Mac の提案フォルダの `COMMON_RULES.md` と `architecture-reviewer.md` をこのリポジトリに取り込み、`CLAUDE.md` と照らし合わせてから決めたい（このリポジトリには無いので、Mark に渡してもらう必要がある）。Obsidian に別の写しを手で持つのは、Codex 案自身が言うとおり食い違いの元なので、Obsidian は同期先（読むだけ）にする
5. **「仮想Mark の推測で範囲は広がらない」に賛成。** `VIRTUAL_MARK.md` も同じ考え（§3 が §2 に優先）。Codex 案の「公開・送信・課金も、個別に許可範囲があればその中で自走できる」は、憲章 I-5（取り消せない操作は Mark の明示の許可か、文書にした自走範囲の中でだけ）と同じ考え方。違うのは今の自走範囲で、`VIRTUAL_MARK.md` §3 は公開・送信・課金を常に確認の側に置いている。Codex 案を採るなら、その自走範囲を広げる話になる。今は広げない（推奨）
6. **Sakana の扱いは一致。** Fugu の性能は自己申告で、学習済みの指揮役を再現したとは言わない。TreeQuest（AB-MCTS）は、正解判定やテストがある難しい課題だけに後で入れる、に賛成（Claude 案の探索予算「高」の中身として）

## 5. Codex の調査で分かった、原本（AI NEWS Select）の問題

- **Jev の Score**: 原本の判断層も、Jev の小数の答えを整数しか受け付けない形らしい（Codex の静的調査。「ローカル文書に小数の実応答が記録」とある）。ルミナスでは今日直した（`docs/jev-value-study.md` §10、コミット a1e7102・b4c679d）。Codex によれば原本の Jev は今は重複の警告に使われていて、Score を使っていなければ実害は無い。使っていれば、その答えはほぼ毎回 Claude に回るか既定値になっている
- **Codex の再試行**: 原本のラッパーは失敗（0 以外の終了）すると同じ作業領域で再試行する（Codex の静的調査）。途中の変更が重なるおそれ。ルミナスの版は「失敗かつ無変更のときだけ、別のモデルで 1 回」にしてある
- **ルミナスからは直さない**（不変条件 6）。Mark から Fable5 の司令塔に、ルミナスの修正（`orch/decisions.py` の `_top_level` とテスト）を参考として伝えることを勧める

## 6. Mark に決めてほしいこと（Claude 案 §6 の 8 点に追加）

1. **実行制御を独立の構成要素にするか**（推奨: する。Phase 1 は全体の停止スイッチ・失敗の種類の表・評価の版だけをファイルで。管理プロセスと SQLite は Phase 2 の終わりに実測で決める）
2. **鍵の控えの置き場**（推奨: 平文の `.env` の写しをやめ、macOS のキーチェーンかパスワード管理アプリへ。`tools/set_env_key.sh` の変更は指示書 → Codex → 審査で。PW Checker の登録の見直しは Mark か Fable5 の司令塔）
3. **共通ルールの正典を 1 つにするか**（推奨: する。Codex の `COMMON_RULES.md` と `architecture-reviewer.md` を渡してもらい、`CLAUDE.md` と照合してから決める）
4. **原本の Jev Score と Codex の再試行を Fable5 の司令塔に伝えるか**（推奨: 伝える。Score の修正の参考を渡し、原本が Score を使っているかの確認を頼む）
5. **自走の範囲を広げるか**（憲章 I-5 は自走範囲の中なら取り消せない操作も許す。今の `VIRTUAL_MARK.md` §3 は公開・送信・課金を常に確認にしている。Codex 案はこれを個別の許可範囲で自走できるようにする案。推奨: 今は広げない）
6. **Codex 案 §11 の「実装前に確定する 4 項目」**: 最初の用途の優先順位（Codex 案は「根拠のある調査・設計・コード改善の下準備」に絞る。推奨: 賛成）、有料の呼び出しの上限（Claude 案 §6-5 と同じ論点）、外部操作の許可範囲（上の 5 と同じ）、Mac が止まっている間も動かす必要があるか（推奨: 今は不要。必要になったら常時稼働の置き場を別に選ぶ）
7. **AI NEWS Select との接続の形**: Codex 案 §9 の「版・内容ハッシュ・根拠・審査・期限を付けた成果物を Fable 側が取り込む一方向の受け渡し」（推奨: 賛成。Claude 案でも接続は Phase 4）

## 7. この回答の限界

- Codex 案が参照する `reference_fable.md`・`independent_review.md`・`COMMON_RULES.md` は読んでいない（このリポジトリに無い）
- 原本の Jev Score の問題は Codex の静的調査の報告で、司令塔は原本のコードを見ていない（原本は読むだけの約束で、このクラウド環境には無い）

## 8. 用語

| 用語 | 意味 |
