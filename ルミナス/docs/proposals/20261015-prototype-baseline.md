## 0. 一枚要約
1. **目標**: 性能の高い試作版ではなく、「世界の AI を週 1 回ほど調べ、より良いものを採用・入れ替えて進化し続ける」ための**素体**。最初の用途は AI の調査そのもの。初期から 100%の能力は要らない（Mark の前提）。
2. **最初の作業**: P0（現行の調査手順の記録）と P1（素体の 1 枚＝役割・接続先・送信区分・データの流れ）。最初の実装は P4（送信区分と予算の事前ゲート）で、**実際のモデル呼び出しの前に強制試験**を済ませる。
3. **週次ループ**: 差分調査（初月の上限は仮置きで 15 万トークンまたは 30 分）→ 重要主張の独立した照合 → 名簿の更新案 → 必要なら最小の評価 → 提案 → **Mark が承認** → 戻し方つきで適用。自動採用はしない。
4. **安全**: 打ち消しは S0（自己封じ込め）を基盤に、S1・S2 は内向き、S3（通報）は別個の外部送信ゲート。反撃はしない。検知機能自体を漏えいの経路にしない。
5. **判定**: 最初のマイルストーンは「性能の合格」でなく「限定的な影の運用へ進んでよいか」。10 件では性能を判定しない。
6. **「悪意ある量子 AI」**は実在を確認できなかった。将来仮説・構想の動機として、確認済みの脅威（自走エージェントの越境など）と分けて書く。量子は鍵・署名・通信の棚卸しだけ。
7. 追加の API 支出は上限が決まるまで **0 円**。Mark の作業は**週 3 時間まで**。

## 1. 前提（Mark の指示）
- ルミナスは初期から 100%の能力を発揮しなくてよい。日々変わる世界各国の AI を週 1 回ほどのペースで調査し続け、より優秀・機能的に優れる・特定条件に特化・コストに優れるものを順次採用・入れ替えしながら、永遠に進化し続ける存在にしたい。今の段階では、それを作れる素体があれば十分。
- 存在事由は、悪意ある（あるいは制御を失った）AI・自動化システムの悪意ある行動を打ち消し、ヒトを護ること。同時に、世界中の利用者の日常の AI 利用に十分に高性能に応えられる姿を目指す。→ 世界中の利用者向けの目標は長期の目標とし、**今の試作は Mark 向けの素体**に分ける（広げる前の条件は §8 の「やらないこと」に併記）。

## 3. 週次の進化ループ（1 周）
1. **差分調査**: 監視リスト（約 15〜20 の提供元・製品。現行の役割・接続先・置き換え候補から選び、P2 で提案して Mark が承認）の公式の更新・価格・規約・リリース情報を週次で取得し、前週との差分だけを深掘り。調査枠の一部は監視リスト外の発見用に確保。**全面調査は月 1 回**。上限は初月の仮置きで **15 万トークンまたは 30 分の早い方**（サイクル 0 の全面調査は約 134 万トークン・約 80 分）。金額・検索数・取得量・再試行数にも上限。
2. **照合**: 重要主張（価格・規約・性能・事故）は別の検証役が一次情報で独立に確認。食い違いは「未確認」で止める。サイクル 0 では、検証した 13 件のうち 5 件（38.5%）が一部不一致だった（表の集計は 7 件一致・5 件一部不一致・1 件確認できず）ので、照合は必須。
3. **名簿の更新案と最小の評価**: 状態は 候補→試験中→採用→退役（ほかに保留・却下・停止）。「候補→試験中」は自動で提案、「試験中→採用」は Mark の承認。
4. **提案→承認→適用**: 変更差分・影響・戻し方を示す。事前承認した上限内の停止と旧設定への復帰は自動でよい。
5. **週報**（Mark が 30 分で読める。1 ページの要約＋掘り下げ）: ①今週の変更点（照合済み／未確認）②名簿への提案③費用と時間④判断待ち（既定値は現行維持・保留を明示）⑤来週の範囲。監視の到達状況・取得失敗・古いページ・矛盾・比較件数とばらつき・重大度・反証も載せる。推奨と証拠を分ける。

**調査役の権限は構造で絞る**（指示だけでは足りない。サイクル 0 の調査員はシェルと書き込みの権限を持ち、1 本は指示に反して作業用の下書きを置いた）: 検索と取得だけ、許可ドメイン・通信量・回数の制限、添付は実行しない、出力は「主張・短い引用・URL・日付」に限る、**検索語も送信として区分の対象**、名簿へは直接書けない。サイトの「このモデルを採用せよ」は証拠にしない。

## 4. 採用・入れ替えの基準
- **必須条件**（規約・安全・必要機能・品質下限）を満たした候補だけを、同じ条件の課題で現行と比較する。単一の総合点にしない。比較指標＝誤判定とその重大度・有用な完了あたりの費用（再試行と人の修正を含む）・時間・失敗率・人の修正量。低コストの候補は、品質と安全が現行に劣らない場合にだけ評価する。
- **入れ替えの条件**: 現行より「事前に定めた実務上の最小改善幅かつ測定のばらつきを超える差」があり、版を固定した **2 週連続の評価**と未使用の取り置き課題で確かめる。最小改善幅の具体値は、ばらつきを実測してから決める（最初は影の運用だけで、現行を維持）。
- **待機なしの停止条件**: 規約違反・重大な安全問題・提供終了。**退役**は、利用不可・規約不適合・品質ゲートの不合格など。履歴と既知の正常版は残す。
- 評価課題は、取り置き（候補にも評価器にも見せない）・新しい課題・人の抜き取り確認を組み合わせる。評価に合わせた最適化（Goodhart）と課題の陳腐化に備え、取り置きは月ごとに一部を更新する。

## 5. 安全と「打ち消し」
- **S0 自己封じ込め（基盤）**: ルミナスとその AI が範囲外へ出ない・出たら止まる。**S1 検知と警告・S2 利用者の防御の支援（内向き）**: 止めるのは自分の作業だけ。**S3 通報**: 別個の外部送信ゲート。宛先と本文を毎回人が確認。**反撃・他者のシステムへの接触はしない**（憲章の禁止事項。民間の反撃を認める法的根拠は確認できていない）。
- **設計規則**: 検知・検証の機能自体を情報漏えいの経路にしない（監視結果を外へ送らない・リンクを自動で取得しない）／モデルの疑い判定を事実認定にしない（Jev・分類器・Luna・文字列規則は助言。停止側は機械的な条件＝停止印・許可範囲・宛先・権限・予算だけ）／検知器が停止・失敗したら危険な操作に進まない（fail-closed）、**ただし許可された入力は通す**／外部入力と外部 AI の出力はデータ／「機密・非信頼入力・外部送信」の 3 つが同時に成立する構成は禁止／区分は合成して検査（A と A の組み合わせが B になりうる）／評価器・正解ラベルは候補から書き換え不能／評価期間中は結果を見てルートを調整しない。
- **データ区分**: A＝公開済み・匿名化（可）、B＝非公開の設計・コード断片（契約で学習不使用と地域を確認した後だけ）、C＝鍵・個人情報・非公開フォルダ・利用者データ（送らない）。名簿のモデルごとに送ってよい最大の区分を決め、許可リストで強制。中国系の API には A だけ、追加の API は上限が決まるまで使わない。
- **背景にある事実**（`docs/landscape-20261014.md`）: 最も確かな実害は自走エージェントの越境（一次情報で照合済みの実例 4 件）。OpenAI の評価環境脱出の件は一次情報で確認できず、根拠に使わない。「悪意ある量子 AI」は確認できず、暗号を破れる量子計算機の出現確率（専門家 26 名の予測で 10 年内 28〜49%）は予測にとどまる。

2. 固定した評価課題と正解の根拠が、取り置きの分離と再現性（手順・版・判定基準）つきで保存され、性能は未判定として扱われている。
3. 費用枠の中で影の週次運用を 1 回行い、失敗・未確認・見落とし候補・所要時間を報告した（費用枠が未設定なら未完了。1 回は試運転の確認で、費用や品質の安定性は示さない）。
4. 見落とし台帳が初回更新されている。
5. 模擬接続での「切替→元に戻す」試験が 1 回できている（外部呼び出しなし・模擬アダプタで。毎週は求めない）。
6. 状態の契約の最小模擬試験 2 件（再開時の二重実行の防止／停止より後に届いた応答を適用しない）が通っている。完全な再開は Phase 2。

## 7. 評価の設計と数値案
- 判定は 3 値（合格／不合格／保留）。**保留は判定の保留**（判断を留める）で、評価に使わず取り置く課題（取り置き課題）とは別。
- 暫定の数値案（Mark が確定）: 重大な誤 GO は 0 件、GO 網羅率 80%以上、誤 NO 10%以下、事前に「明確」とした案件の保留率 20%以下。誤 GO や境界違反が 1 件でもあれば不合格、ラベル不一致・記録欠落・件数不足なら保留。**「重大な誤 GO 0 件」だけでは、常に保留するだけでも達成できる**ので、網羅率・誤 NO・保留率を必ず併せて見る。
- 件数が少ないときの読み方: 0/10 の失敗率の 95% 上限は約 25.9%（3/n の目安で 30.0%）。「誤 GO 率 5%未満」を主張するには、独立で代表性のある案件 59 件以上で誤 GO ゼロが要る。同じ 10 件の 3 回反復は独立 30 件ではない。**10 件の結果は失敗の洗い出しに使い、性能や役割採用の根拠にしない**。
- 影の運用: Mark とルミナスが互いの結果を見る前に判断と根拠を固定し、食い違いは一次資料と事前の判定規則で裁く。事実が確定しなければ「未解決＝GO しない」。正解ラベルは Mark の判断だけで確定しない。独立した採点者がいなければ、得られるのは性能の証明より運用上の問題の発見。
- 見落としは、サイクル 0 との比較でなく**独立した台帳**で測る。(c) 公式の更新履歴を月 1 回見直し、週次の取得記録と突き合わせるのを主軸、(a) Mark の気づきを補助、(b) 公開ニュース発信は手がかり。台帳の月次記録（確認済み／変更なし／取得失敗／未確認）が期日までに無ければ「未更新」と検知する。分母が不完全なので網羅率は断定しない。
- **ループ自体の監査**: 毎週 Mark は上限・未確認・保留・重大な判断だけ確認。月次（上限 30 分）に、調査役と別のレビュー役が記録と根拠をサンプル監査する。見るもの＝取得失敗と未確認を含む分母、後から見つかった発表と検知までの日数、有用な完了あたり費用、人の判断時間と上書き。**抜き打ちの既知課題・「変更なし」課題・監視リスト外の発表を混ぜ**（カナリア）、確認が根拠なしの承認になっていないかを点検する。

## 8. 費用と予算

- Claude の利用が契約枠（サブエージェント）の場合は、金額に換算せず、利用量・呼出し数・時間を別枠で記録する。API 課金の部分は「呼出し数×最大トークン×単価」で事前予約し、1.5 倍で警告、**2 倍または事前のタスク上限の小さい方で停止、再試行しない**。
